Описание бага (предположение)
-----------------------------
При предиктивном звонке оператору прилетает новый лид (комната `lead-N2`), но клиентский сокет ещё не успел корректно отписаться от старой комнаты `lead-N1`. 
В это же время по старому звонку (`lead-N1`) срабатывает хук на бэке (завершение разговора, изменение статуса и т.п.) и уходят сокет‑события, которые попадают в браузер, когда UI уже считает активным нового лида. 
В результате новый звонок/карточка лида ломается (неконсистентное состояние, не те статусы, странное поведение кнопок и т.д.).

Ниже — варианты, как такую гонку попытаться воспроизвести или эмулировать.

1. DevTools + принудительное «залипание» в старой lead‑комнате
-------------------------------------------------------------
Идея: искусственно сделать так, чтобы фронт не выходил из старой комнаты `lead-*`, а потом инициировать новый звонок.

Шаги (ручной эксперимент):
1. Залогиниться оператором в dev/qa окружении.
2. Открыть DevTools → Console.
3. Патчнуть клиентский код, чтобы не выходить из старых каналов:
   - В `caller.js` функция `joinLeadChannel(leadId)` сначала делает:
     - фильтр по `socketChannelsList`
     - `leaveSocketChannel` для всех `lead-*`
     - потом `joinSocketChannel('lead-' + leadId)`.
   - Через консоль сделать:
     ```js
     window.__test_original_joinLeadChannel = window.joinLeadChannel;
     window.__test_original_leaveSocketChannel = window.leaveSocketChannel;
     window.leaveSocketChannel = function (channel) {
       console.log('TEST: skip leaveSocketChannel for', channel);
     };
     ```
4. Инициировать первый звонок (лид А) любым доступным способом:
   - через API `v1/lead/create/` → `?controller=vats&method=dialer`, как в текущих UI‑тестах;
   - либо через реальный поток звонков, если он есть на dev.
5. Дождаться появления карточки лида А (`#call-session[data-lead-id="A"]`).
6. Не завершая звонок А, инициировать следующий дозвон (лид B) тем же способом.
7. Наблюдать, что клиент:
   - остаётся подписан и на `lead-A`, и на `lead-B`,
   - продолжает получать сокет‑ивенты по старому лиду после появления карточки нового.
8. Во время этого потока смотреть:
   - `localStorage.lastLeadId`,
   - состояние элементов `#call-session`, `#lead-preloader`, `#callStatus`,
   - сообщения `Liner Bot` (особенно события `leg-is-disconnected`, `auto-prepare-call`, AI‑события).

Цель: получить стабильный сценарий, при котором ивенты по старому лиду визуально ломают UI нового.


2. DevTools + искусственная задержка отписки от старой комнаты
-------------------------------------------------------------
Если полностью отключать `leaveSocketChannel` слишком грубо, можно эмулировать задержку:

```js
window.__test_original_leaveSocketChannel = window.leaveSocketChannel;
window.leaveSocketChannel = function (channel) {
  console.log('TEST: delayed leaveSocketChannel for', channel);
  setTimeout(() => window.__test_original_leaveSocketChannel(channel), 3000);
};
```

Дальше повторить сценарий из пункта 1:
- первый звонок (лид А),
- пока UI ещё живёт, инициировать второй (лид B),
- следить, что в течение ~3 секунд клиент реально подписан на две комнаты и успевает принять «завершающие» ивенты по старому лиду, когда новый уже активен.


3. Использование режима тренажёра (training_mode) для генерации вызовов
----------------------------------------------------------------------
В `caller.js` есть логика тренажёра (`trainingModeIsEnabled`, `#training_status`, `socket.on('call-simulator-call', ...) → loadCallingLead()`).

Идея: 
- включить тренажёр, чтобы гонять звонки без реальной телефонии,
- комбинировать это с патчем `leaveSocketChannel`.

Шаги:
1. Включить тренажёр из UI:
   - чекбокс `#training_status`,
   - выбрать хотя бы одну опцию `training_options[]`.
2. Убедиться, что при включённом тренажёре звонки идут через `call-simulator-call` и `loadCallingLead()`.
3. Через DevTools:
   - патчнуть `leaveSocketChannel` (как в пунктах 1/2),
   - дополнительно логировать присоединения к каналам: обернуть `joinSocketChannel` и `socketChannelsList` в логи.
4. Сымитировать «рабочий день»:
   - несколько последовательных тренажёрных звонков без паузы на отписку,
   - быстрый приём/завершение звонков,
   - наблюдать, в какой момент UI ломается.

Плюс: не нужна настоящая телефония и Voximplant, всё крутится локально в браузере.


4. Моки бекенда для socket.io
-----------------------------
Более тяжёлый, но управляемый вариант — полностью замокать сервак сокетов.

Идея:
- перехватить инициализацию `socket` (например, через DevTools `override` `io.connect`),
- вместо настоящего URL подключиться к локальному тестовому socket.io‑серверу,
- со стороны мок‑сервера посылать события в произвольном порядке и с нужными задержками.

Вариант реализации:
1. Локально поднять небольшой Node‑скрипт с socket.io‑сервером:
   - комнаты `call-center-general`, `lead-<id>`,
   - события: `predictive-signal`, `leg-is-disconnected`, `auto-prepare-call`, `call-simulator-call` и т.п.
2. В DevTools до инициализации настоящего сокета выполнить:
   ```js
   window.io = {
     connect: function () {
       return window.__test_mock_socket; // собственная реализация
     }
   };
   ```
3. Через мок:
   - подписывать клиента последовательно на `lead-A`, `lead-B`,
   - намеренно НЕ слать `leave` по старой комнате,
   - затем слать «завершающие» ивенты по А после того, как в UI уже открыт B.

Это даёт полный контроль над порядком и временем прихода событий и позволяет точно зафиксировать воспроизведение.


5. Массовый прогон через API диаллера
-------------------------------------
Идея: повысить шанс гонки за счёт нагрузки.

1. Написать небольшой Python/JS‑скрипт, который:
   - массово создаёт лидов через `v1/lead/create/`,
   - в цикле регулярно дёргает `?controller=Vats&method=dialer`,
   - параллельно меняет статус оператора (`available`/`busy`/`post_call`) через API.
2. На фоне держать открытую операторскую вкладку и включённый `browserLogRecorder`.
3. Ищем моменты, когда:
   - в логах/консоли появляются ошибки JS,
   - UI залипает на старой карточке/странно показывает статус,
   - звонок приходит, но кнопки взаимодействия не работают.

Это скорее полу‑стохастический способ поймать баг, но полезен для стресс‑тестов.


6. Идеи для автотестов
----------------------
Варианты тестов, которые можно/нужно добавить:

1) UI‑тест (Playwright) с патчем сокетов
   - Базироваться на уже существующем `TestDialerOptimized` (`tests/test_dialer_optimized.py`).
   - Шаги (на уровне автотеста):
     1. Логин оператором.
     2. В `page.evaluate` патчнуть `leaveSocketChannel` (делать `noop` или задержку).
     3. Создать лида А через `v1/lead/create/` и запустить дозвон через `dialer`.
     4. Дождаться UI звонка А.
     5. Создать лида B, снова вызвать `dialer`.
     6. Убедиться, что:
        - карточка лида B открыта (правильный `data-lead-id`),
        - кнопки `#finish_call`, `#callStatus`, `#save-call-result-btn` доступны,
        - нет фатальных ошибок в консоли (Playwright умеет слушать `page.on('console', ...)`).
   - На старте можно пометить тест `@pytest.mark.skip` или `xfail` до стабилизации сценария.

2) API‑интеграционный тест (моки телефонии)
   - Использовать существующую конфигурацию `config/telephony_test_config.json` и (при необходимости) отдельный JSON с мок‑данными.
   - Идея: на уровне API проверить состояние диаллера и сущностей звонка, когда:
     - по предыдущему звонку приходит хук о завершении,
     - одновременно стартует новый предиктивный звонок на того же/другого оператора.
   - Проверки:
     - оператор не уходит в «битый» статус,
     - новый звонок не отменяется/не перескакивает в некорректный статус.

3) Юнит/компонентный тест для логики каналов
   - Вынести (или хотя бы документировать) логику `joinLeadChannel`/`socketChannelsList` в отдельный JS‑модуль;
   - покрыть тестами (например, Jest) простые инварианты:
     - после `joinLeadChannel(B)` в `socketChannelsList` нет `lead-A`,
     - последовательные вызовы с ошибками/исключениями не приводят к множественному членству в разных `lead-*`.


7. Связь с обычными (непредиктивными) звонками
---------------------------------------------
Хотя баг проявился на предиктивных звонках, сама суть гонки — «старые сокет‑ивенты по старому лиду, когда UI уже переключился на новый» — релевантна и для обычных звонков:
- те же каналы `lead-*`,
- те же события `leg-is-disconnected`, `new-call-record` и пр.,
- те же глобальные флаги в `localStorage` (`lastLeadId`, `firstDisconnectedNotifyIsShowed`, `nextCallIsScheduled` и т.д.).

Поэтому:
- сценарии из этого файла стоит обкатать как минимум в тренажёрном режиме и для обычных звонков (через `call-simulator-call`),
- автотесты лучше формулировать нейтрально: «смена лида/карточки при ещё живых ивентах по старому lead‑каналу не ломает UI и состояние звонка».
